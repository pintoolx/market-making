你是一位具備 TypeScript、Web3、交易系統、編譯器與安全測試經驗的資深工程師。

請在目前 repository 中實作一個名為「SwapVM Strategy Builder」的 MVP。

這是一個讓使用者透過自然語言對話，組合 SwapVM 既有功能，建立自己的做市策略的產品。

請交付可執行程式、測試與文件，不要只提供架構建議。

先閱讀現有 repository、AGENTS.md、套件鎖定檔、package scripts 與環境設定，沿用既有架構。只有沒有現成架構時，才採用本 prompt 的預設技術選擇。


一、產品定位與範圍

核心流程：

自然語言需求
→ 結構化策略草稿
→ 功能與語意驗證
→ 確定性編譯
→ 情境預覽與完整交易模擬
→ 使用者審閱
→ 匯出或由使用者錢包確認註冊。

「custom strategy」指交易對、既有曲線、價格區間、費率與已驗證條件的客製化組合。

不是讓 LLM 自由生成 Solidity，也不是自主交易機器人。

本版沿用 Aqua-backed SwapVM：
- 使用已部署並核對過的 AquaSwapVMRouter。
- 使用官方 Aqua 介面進行必要的 ship/dock 與餘額查詢。
- APP 是已核對的 SwapVM router，不是自行部署的 AquaApp。
- ERC-20 授權、RPC 查詢與使用者錢包確認屬於必要整合，不是新增交易邏輯。

明確禁止：
- Custom AquaApp。
- 自訂 SwapVM router 或新 opcode。
- Extruction。
- 自訂 maker/taker hooks。
- 任意外部 pricing contract 或 fee provider。
- 自動 rebalance、auto-recenter、自動跟价與 keeper。
- 跨協議換匯、借貸、槓桿、避險與跨鏈資金操作。
- 後端保管使用者私鑰或助記詞。
- LLM 直接產生並執行任意 calldata。
- 未經使用者確認的授權、簽署或廣播。

允許本機與 fork 測試使用測試 harness 或上游合約，
但不得在開發過程中部署新的 production 合約或操作使用者真實資金。


二、先核對部署與能力，不要直接開始猜 API

建立版本化 deployment manifest，至少包含：

- profileId、chainId。
- routerAddress、aquaRegistryAddress。
- 合約 code hash 與 ABI。
- 對應 source tag、commit SHA、opcode table。
- 固定的 swap-vm-sdk、aqua-sdk 版本。
- router 與 Aqua 的實際 binding。
- 驗證時間、block number、block hash。
- 相容性證據、測試狀態與分發狀態。

不能從 main/master、README 範例或記憶直接推導正式部署。

同名 router、相同地址或 SDK 有某項功能，都不是充分證據。
缺少 RPC 或部署證據時，標示 unverified，允許離線開發，
但禁止開啟真實交易入口。

建立 capability registry，分開記錄：

sourceImplemented
sdkEncodable
runtimeVerified
compositionTested
productEnabled
routingCompatible

不要用一個 supported=true 混合所有層次。

每項功能必須有參數 schema、單位、限制、前置條件、
side effects、適用 recipes 與來源。

未知 opcode、reserved gap、未知 traits，
即使鏈上可能不立即 revert，也必須被 compiler 拒絕。


三、本版策略功能

優先實作：

1. Constant-product / XYC AMM。
2. 固定上下限的 Concentrated AMM。
3. 經核對 SDK、原始碼與測試後的 Pegged AMM。

允許的附加功能，僅在目標 profile 與組合均驗證後啟用：
- 固定 LP 輸入費。
- 策略 deadline。
- Decay。
- 經核對的方向與存取條件。

Protocol fee、dynamic protocol fee 預設關閉，
不要把它們和固定 LP fee 混為一談。

Limit order、partial fill、Dutch auction、TWAP/DCA，
不得只因通用 SwapVM 或 SDK 有實作，
就在目前的 Aqua profile 宣稱支援。

先完成 XYC vertical slice，再增加其他模型。
不要為了湊功能清單，交付假 builder 或假的鏈上整合。


四、對話行為

產品內 agent 使用繁體中文，支援多輪修改同一份草稿。

每輪應輸出：
- 使用者需求摘要。
- 當前策略摘要。
- 已確認參數。
- 缺少的參數。
- 不支援的需求。
- 風險及下一步。

只追問真正缺少或矛盾的資訊，不重問已確認內容。

必須釐清：
- 目標鏈與 maker。
- token 地址，而不只是 symbol。
- 實際可用資產與數量。
- 曲線及必要參數。
- 費率。
- 期限或明確的無期限選擇。

使用者說「現在價格上下 5%」時：
- 取得可追溯的參考價格，或請使用者指定中心價。
- 記錄來源與時間。
- 算出建立當下的固定上下限。
- 明確說明這不是自動跟價或自動 rebalance。
- 要求使用者確認具體數值。

使用者修改任何實質參數時：
- 建立新 revision。
- 顯示 diff。
- 重新驗證、編譯及模擬。
- 使先前的交易確認失效。

每個需求都要分類：
- onchain_enforced。
- preflight_only。
- informational。
- unsupported。

onchain_enforced 必須由確定性 validator 根據 capability
registry 判定，LLM 不得自行宣稱。

例如：
「每次 taker 的滑價限制」
「策略最低賣價」
「maker 庫存底線」
「全部策略每日成交上限」
是不同需求，不得用同一個欄位或 guard 假裝全部實現。

超出範圍時，明確說明不可實現的部分。
不得默默刪掉需求，也不得自行改用新合約或其他協議。


五、資料模型

建立獨立的：
StrategyDraft
ValidatedStrategy
CompiledStrategy
SimulationReport
TransactionPlan

StrategyDraft 至少包含：
- draftId、revision、owner、backendProfileId。
- maker、chainId。
- baseToken、quoteToken。
- allocations。
- model：xyc / concentrated / pegged 的 discriminated union。
- 各模型必要參數。
- 型別化 modifiers。
- 原始需求與 enforcement 分類。
- assumptions、missingFields、unsupportedRequirements、warnings。
- 定稿後固定的 salt。

CompiledStrategy 至少包含：
- normalized spec 與 hash。
- recipeId、recipeVersion、manifest hash。
- 官方格式的 program 與 encoded order/strategy。
- 正確且分開命名的 programHash、orderHash、strategyHash。
- 可讀的 instruction trace。
- 實際 traits、receiver、access conditions 與 fee 語意。

草稿可以缺少資料；可編譯／可送出的版本不能保留未解決欄位。

不要把應用層 JSON hash 當成協議的 strategyHash。


六、數值與 compiler

金額及定點計算使用 bigint 或經驗證的精確數值工具。
JSON 用十進位字串保存大整數。

禁止用浮點 Number 計算 raw amounts、價格平方根、
匯率或內部 fee encoding。

正確處理：
- Token decimals。
- base/quote 的人類語意。
- 合約與 SDK 使用的 token 排序。
- 價格取倒數後的 min/max 交換。
- raw price 與定點尺度。
- maker/taker 方向。
- 四捨五入。
- 一般 bps 與 SDK／合約的內部尺度。

SDK helper 已轉換單位時，不得再次轉換。

Concentrated 策略不可一律假設需要 50/50 inventory。
依實際曲線與庫存檢查，也不可自動到其他 DEX 補資產。

區分 WETH 與原生 ETH，不偷偷 wrapping。
特殊 ERC-20 行為未經測試前預設不支援。

LLM 只輸出結構化意圖與草稿 patch。
Compiler 是獨立、確定性且可測試的程式。

同一份 validated spec、salt、recipe version 與 manifest，
必須產生相同 bytes。

只允許經驗證的 composition recipes。
不要讓使用者自由重排 opcode、提供任意 jump target，
或把概念流程圖的順序當成安全的執行順序。

每個 recipe 固定合法結構、可配置插槽與相容參數。
編譯後反解 bytes，核對是否與 spec 一致。

必須拒絕：
未知指令、非法長度、不相容組合、未核對分支、
向後跳轉、能跳過 guard 的路徑、重複收費、
任意 external target 與不允許的 hooks。


七、Agent Tools 與資金權限

建立以下應用層工具；這些名稱不是官方 SDK API：

getCapabilities
resolveTokens
getWalletInventory
createOrPatchDraft
validateStrategy
compileStrategy
previewScenarios
simulateLifecycle
prepareRegistration
inspectStrategy
prepareCancellation
exportStrategy

每個工具有 schema、結構化錯誤、來源、時間與版本資訊。

不要給 LLM：
unrestricted sendTransaction
signTypedData
approve
eval
executeSolidity
任意 calldata 執行工具。

工具只能準備 TransactionPlan。
實際簽署由獨立 wallet UI，在使用者明確確認後完成。

確認摘要必須從實際 decoded payload 產生，
而不是依賴 LLM 自由描述。

不同使用者的草稿、wallet ownership、revision 與
confirmation 必須隔離。

Token metadata、第三方文件與工具回傳文字是不可信資料，
不得用其中的指示改變 agent 權限或交易內容。


八、報價與模擬

分開呈現：
1. 數學／情境預覽。
2. 固定 block/context 的 quote。
3. 完整交易模擬。

尚未 ship 的 Aqua-backed 策略，不可假裝已能直接做
目前鏈上的 quote。可在 fork 先模擬 approval＋ship，
再測試 quote/swap，但必須標明測試條件。

quote 成功不等於 settlement 成功。
完整模擬須涵蓋：
- maker/taker balance。
- 正確 spender 的 allowance。
- access gate 與 caller context。
- 真實 transfer path。
- fees 與 token 行為。
- 成交後餘額。
- dock 後不可再成交。

比較 quote/swap 金額時要保持相同起始 state、
timestamp 與 caller context。
不能保證不同區塊的報價與成交一定相同。

分開標示：
mock
local-upstream
fork-with-overrides
fork-real-context
live-read

缺少 RPC 或 resolver credentials 時，
不得移除 gate 或偽造條件來宣稱真實整合成功。

至少測試雙方向、exact-in/out、大小額、
低庫存、區間邊界、deadline 前後與連續成交。


九、註冊、取消與 shared inventory

真實交易入口預設關閉。

TransactionPlan 顯示：
chainId、maker、目的合約、function、參數、
calldata hash、value、授權、gas 與前置條件。

僅允許核對過的合約、ABI 與 selectors。
簽署前核對 payload 與已審閱 spec 一致。

依實際拉款方設定 allowance，
不要因為使用 SwapVM 就盲目 approve router。

預設準備必要的有限授權。
調整既有 allowance 可能影響其他策略，必須提醒。
不要默默要求 unlimited approval。

Aqua-backed 模式不要誤做成一般 EIP-712 簽單流程，
也不要猜測 Aqua registry 的 signing domain。

使用者明確確認後才開啟錢包簽署。
處理拒簽、錯鏈、revert、timeout、replacement 與重試。
沒有成功 receipt 與鏈上核對，不顯示註冊成功。

取消走實際 dock 流程。
UI 停用不是鏈上取消；dock 也不等於撤銷 ERC-20 allowance。

修改已註冊策略時，只建立新草稿並準備必要操作，
不要宣稱原策略可原地修改或多筆交易天然原子化。

分開展示：
wallet balance
allowance
每個策略的 virtual balance
已知其他 commitments
資料未涵蓋的部分

不能把多個 virtual balances 相加當成真實資本。
不能宣稱某策略成交會自動同步縮減其他策略帳本。
資金預檢也不等於鏈上全域預留。


十、策略註冊與成交分發分開

獨立保存：
- 草稿／驗證狀態。
- 鏈上註冊狀態。
- 模擬可信度。
- access/fillability 狀態。
- discovery/routing 狀態。

ship 成功不等於已獲得聚合器訂單流。

核對選定 recipe 與通路的存取要求，
包含必要時的 taker 與 tx.origin 差異。

不要把特定官方模板的 gate 說成所有 Aqua 使用都相同。
也不要移除 gate 後仍宣稱與原分發路徑相容。

本版不開發 resolver。
分發未接入時，仍可交付建立、匯出與註冊能力，
但必須顯示未接入／未驗證，不保證成交、收益或 APY。


十一、技術選擇與驗收

沿用既有專案；空白專案可選：
TypeScript strict、React/Next.js、viem、Zod、Vitest。
需要時加入 Playwright 與 Foundry fork tests。

版本先核對相容性後鎖定，不盲用 latest。

將 schema、capability registry、compiler、simulation、
wallet preparation 與 conversation adapter 分離。

LLM provider 可替換；沒有模型 API key 仍可透過明確
標示的 deterministic fixtures 測試核心流程。

至少包含以下驗收案例：
- XYC 原生策略可編譯，不部署新合約。
- Concentrated 固定區間、費率與價格方向正確。
- 「現在上下 5%」產生固定 snapshot，不是自動跟價。
- 多輪修改有 diff，舊確認失效。
- 6/18 decimals 與 token 排序交換正確。
- Unsupported rebalance/DCA 不被偷偷替換成普通 LP。
- 未知 opcode、traits、hooks 被拒絕。
- SDK／部署／opcode 不相容時禁止送出。
- quote 成功但 allowance 不足時，不宣稱可成交。
- shared inventory 不被重複計算。
- 缺少 access 或 RPC 不偽裝整合成功。
- 使用者拒簽、交易失敗與取消流程正確。
- 惡意 metadata 不改變權限或收款地址。
- 同一 spec＋manifest＋salt 可重現相同 bytes。
- 不同使用者的草稿與確認彼此隔離。


十二、里程碑與交付物

Phase 0：
盤點 repository，建立 deployment manifest、
capability matrix、schemas、來源與未支援清單。

Phase 1：
完成 XYC 的完整 vertical slice：
對話 → 草稿 → 驗證 → 編譯 → 解碼核對
→ 模擬 → 交易計畫／匯出。

Phase 2：
增加 Concentrated、已驗證的 Pegged、
固定 LP fee、deadline 與安全的原生 modifiers。

Phase 3：
完成使用者 wallet review、ship/dock、
receipt／事件核對及策略狀態展示。

交付：
- 可執行程式碼與啟動指令。
- 固定套件版本與環境設定範本。
- Capability registry、deployment profiles。
- Schemas、recipes、compiler／decoder。
- Agent tools、模擬與交易準備。
- 自動化測試及真實執行結果。
- 架構、安全、限制、來源及 release checklist 文件。
- 支援策略與 unsupported 需求示範。

商用前核對 SwapVM、Aqua、SDK 的實際授權與使用條件。
不要因為不部署新合約，就假設沒有授權問題。
測試通過也不等於第三方安全審計。

先報告 repository 盤點與已確認／未確認能力，
接著直接實作最小 vertical slice，不要只給計畫後停止。

缺少外部條件時，完成可完成的離線部分並列出 blockers。
不要猜地址、偽造交易 hash、隱藏未跑的測試，
或宣稱未完成的真實部署驗證。

完成判準：

使用者需求沒有被偷換；
策略只含目標部署可執行且產品允許的指令；
編碼可重現；
各項條件的實際強制範圍清楚；
模擬可信；
資金操作只能由使用者審閱後簽署。
